# Лабораторный эксперимент: рост агента с паспортом, его потомки и обратная связь

Версия 0.2 · воспроизводится командой `npm run lab` (seed `xonta-lab-1`, повтор даёт те же числа).

## Что проверяли

Работают ли вместе механизмы черновика спецификации, если собрать их из настоящих участников:

- агенты подписывают свои действия своими ключами (did:web), а не ключом оркестратора;
- оркестратор ведёт агентов через шлюз A2O2A и подаёт сигналы;
- владелец выдаёт мандат на потомков, родитель подписывает их родословную, оркестратор проверяет обе подписи и лимиты;
- потомок присылает подписанное предложение улучшения. Оркестратор проверяет его на отложенной выборке и рекомендует слияние, а применяет его владелец;
- вклад потомка фиксируется аттестатом с долей в приросте;
- испорченные правила, подделки и самоуправство отсекаются;
- отзыв предка доходит до потомков.

## Участники

| Участник | Роль | Идентификатор |
|---|---|---|
| Владелец корня | Выдаёт мандат, принимает решения, применяет слияния | свой did:web, только ключ |
| Корневой агент | Нормализует данные (даты, единицы, телефоны, суммы), учится на исправлениях | свой did:web, MCP |
| Потомки | Специалисты по одной категории. Рождаются по сигналу оркестратора | свой did:web, MCP |
| Агент-генератор | Даёт задачи с эталонами: трафик клиенту и отложенные выборки оркестратору. Принадлежит другому владельцу | свой did:web, MCP |
| Клиент | Отправляет задачи агентам через шлюз и присылает исправления неверных ответов | свой did:web |
| Оркестратор | Шлюз, проверки, сигналы, оценки, слияния, аттестаты | did:web эмитента |

Все вызовы между участниками идут через шлюз A2O2A и подписаны. Языковой модели в агентах нет. Агент выводит правила из исправлений перебором гипотез, поэтому результат детерминирован. Проверяется механика паспорта, потомков и обратной связи, а не качество моделей. Модель можно подключить позже вместо этого «ученика».

## Условия

- 10 раундов, около 220 задач трафика за раунд. Новые форматы данных появляются в раундах 1, 3, 5 и 7.
- 2% меток трафика неверны.
- Каждый агент за раунд усваивает не больше 25 исправлений. Это допущение модели, оно имитирует ограниченную ёмкость одного агента. Ниже есть проверка без ограничения.
- Ветвь A: корень и до 3 потомков по мандату (глубина 1), слияние раз в 2 раунда. Ветвь B (контроль): тот же корень один на тех же данных; сигналы владелец не принимает.
- В раунде 6 одному потомку отправлена партия из 40 систематически неверных исправлений (имитация ошибки партнёра по данным).
- Точность измеряется дважды:
  - оркестратор оценивает на своей отложенной выборке от генератора и выдаёт аттестат;
  - лаборатория замеряет на общем эталоне, одинаковом для обеих ветвей.

### Как рождались, проверялись и подписывались потомки

| Потомок | Рождён | Причина | Что проверено перед регистрацией |
|---|---|---|---|
| lab-phones | раунд 1 | сигнал «родить специалиста»: категория «телефоны» занимает ≥20% трафика, а качество в ней на ≥20 п.п. ниже лучшей | мандат подписан владельцем родителя; родословная подписана родителем; категория входит в мандат; лимит 3 потомка и глубина 1 соблюдены; DID на том же хосте, что MCP; домен подтверждён; проверка MCP — признаков не найдено |
| lab-units | раунд 3 | тот же сигнал для категории «единицы» | то же |

Каждый потомок получил аттестат `AgentLineage` от оркестратора: родитель, корень, глубина, владелец, отпечатки мандата и подписи родителя. Проверку владельца потомки унаследовали от корня. `verify_agent` показывает это полем `owner_inherited_from`, поэтому оба потомка получили уровень 2, как и корень. Уровень 3 не получил никто: для репутации политика по умолчанию требует 7 дней жизни и 20 внешних вызовов. Лаборатория длится минуты, и это честное ограничение.

Вклад считается абляцией: насколько хуже было бы слияние без правил этого потомка. Аттестаты `AgentContribution`:

Каждый такой аттестат ссылается на отложенную выборку: генератор, seed и отпечаток.

### Защита

Все попытки отклонены:

| Попытка | Ответ |
|---|---|
| Подделанное предложение: правила изменены после подписи | 400, подпись неверна |
| Предложение вне области потомка | 403 |
| Предложение от незарегистрированного агента | 403 |
| Мандат, подписанный не владельцем | 400 |
| Регистрация потомка не владельцем | 403 |

Каскад: после отзыва корня оба потомка приостановлены, а не отозваны молча. Их уровень по `verify_agent` упал до 0.

Журнал событий собран в дерево Меркла; для аттестата о вкладе выдаётся доказательство вхождения в зафиксированный корень. Отметка OpenTimestamps в лаборатории не получена: нет доступа к календарным серверам.

## Что из этого следует и чего из этого не следует

1. **Потомки ускоряют рост, только когда ёмкость агента ограничена.** С пределом 25 исправлений за раунд у ветви A средняя точность 90–92% против 81% у контроля. Без предела (1000 исправлений, файл `report-budget1000.json`) обе ветви дают 99,6%. Сигнал «родить специалиста» там ни разу не сработал: разрыва между категориями не возникло. Это хорошо: сигнал не рекомендует потомков, когда они не нужны.
2. **Слияние на отложенной выборке защищает родителя, но не пользователей самого потомка.** Испорченное правило не попало в корень, а потомок продолжал отвечать с ним, пока его не исправили новые данные. Отсюда падения «системы» в раундах 6 и 9. Следствие для спецификации: маршрутизатору стоит возвращать задачи родителю, когда свежая оценка потомка в его категории ниже родительской.
3. **Обратная связь только по ошибкам при шумных метках «расшатывает» выученное.** Клиент присылает исправления только на неверные ответы. Если агент уже прав, к нему приходят в основном ошибочные метки. Так потомок «выучил» неверный коэффициент для см (раунд 9) без всякой атаки. Проверка правил по отдельности это поймала. Вывод: в протокол обратной связи нужно добавлять подтверждения верных ответов, а не только исправления.
4. **Предложение проверяется по правилам, а не целиком.** В раунде 7 одно предложение содержало плохое правило (GB) и хорошее (JP). Принято хорошее, плохое отклонено с числами.
5. **Не следует:** что агенты с паспортом лучше в целом. Что модель с потомками всегда выгоднее. Что эвристики проверки MCP ловят всё. Данные синтетические, задачи простые, «ученик» без модели.

## Воспроизведение

```bash
npm install
npm run lab                                              # обе ветви, отчёт в lab/out/report.json и summary.json
FEEDBACK_BUDGET=1000 OUT_NAME=report-budget1000.json node lab/run.js   # проверка без ограничения ёмкости
```

Параметры: `ROUNDS`, `TRAFFIC`, `FEEDBACK_BUDGET`, `MERGE_EVERY`, `POISON_ROUND`, `SEED`.
